# Themes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Colour themes as JSON: Light/Dark/Book plus ~24 ready-made themes, user themes saved in Inky's settings folder, a "Custom" theme holding the last unsaved tweak, and a visual theme editor with a live sample.

**Architecture:** A pure TypeScript theme model (`src/lib/themes/`) parses, validates, derives and resolves a theme to the CSS custom properties Inky already uses; one apply path sets them inline on `<html>` plus a kind class (`light`/`dark`). Rust stores theme files under `app_config_dir()/themes/` and rebuilds the native Theme submenu from entries the frontend pushes. A Svelte dialog edits themes live.

**Tech Stack:** Svelte 5 (runes), SvelteKit static, Tailwind 4, Tauri 2 (Rust), vitest (jsdom), cargo test.

**Spec:** `docs/superpowers/specs/2026-11-19-themes-design.md`

## Global Constraints

- Package manager is pnpm. No new npm or cargo dependencies.
- Light, Dark and Book must render exactly as they do at commit `0354808` (colour values identical).
- Typography is never part of a theme.
- Code blocks keep their fixed terminal palette (`.prose-doc pre` overrides); highlighter pen colours stay fixed.
- Theme files live in `app_config_dir()/themes/`, never in the library. File name `<id>.json`. Custom is `custom.json` with a `basedOn` field.
- Theme ids match `^[a-z0-9][a-z0-9-]{0,63}$`; built-in ids `light`, `dark`, `book`; Custom id `custom`; ready-made ids are prefixed `rm-`.
- File format key `"inkyTheme": 1`.
- Writes are atomic (write `*.tmp`, then rename), like `write_highlights` in `src-tauri/src/lib.rs`.
- Contrast threshold 4.5:1 (body text on page, link on page, sidebar text on sidebar).
- Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Checks that must pass after every task: `pnpm check` (0 errors), `pnpm test`, and for Rust changes `make check`.

## Review Focus

1. A stored active theme id whose file has vanished or become invalid → Inky falls back to Light and says so once (Task 4 test `falls back to light when the active theme is missing`).
2. Hand-edited theme JSON with junk (bad version, bad kind, missing main colour, invalid optional colour, unknown keys, not JSON) → clear rejection or a warning, never a crash or blank styling (Task 1 parse tests).
3. A Book user upgrading keeps the serif look (Task 2 test `book users keep the serif typeface`).
4. Theme names that are emoji-only, very long, punctuation-heavy, or equal to a built-in name (any case) → a valid unique id and a unique name (Task 4 tests on `slugFor` / `uniqueName`).
5. Built-ins resolve to exactly today's values (Task 1 fixture test `built-ins resolve to today's colours`).

## Key mapping (decided here; Tasks 1, 2 and 6 rely on it)

Theme key → CSS custom properties it sets. "Derived" is the value used when the key is absent (non-built-in themes). `P`, `T`, `A`, `S`, `B` are the main colours page, text, accent, sidebar, border.

| Group | Key | Sets | Derived when absent |
|---|---|---|---|
| main | page | `--background` | required |
| main | text | `--foreground` | required |
| main | accent | `--prose-link` | required |
| main | sidebar | `--sidebar` | required |
| main | border | `--border` | required |
| exact | mutedText | `--muted-foreground` | `color-mix(in oklab, T 58%, P)` |
| exact | hover | `--accent` | `color-mix(in oklab, T 7%, P)` |
| exact | tableHeader | `--muted` | `color-mix(in oklab, T 4%, P)` |
| exact | inlineCode | `--prose-code-bg` | `color-mix(in oklab, T 6%, P)` |
| exact | quoteBar | `--prose-quote-border` | `color-mix(in oklab, T 20%, P)` |
| exact | selection | `--editor-selection` | `color-mix(in oklab, A 28%, transparent)` |
| exact | commentMark | `--comment-mark` | `rgb(250 204 21)` |
| exact | tabStrip | `--tab-strip` | light kind `color-mix(in oklab, T 3.5%, P)`; dark kind `color-mix(in oklab, black 12%, P)` |
| ui | card / cardText | `--card` / `--card-foreground` | P / T |
| ui | popover / popoverText | `--popover` / `--popover-foreground` | P / T |
| ui | primary / primaryText | `--primary` / `--primary-foreground` | T / P |
| ui | secondary / secondaryText | `--secondary` / `--secondary-foreground` | tableHeader value / T |
| ui | hoverText | `--accent-foreground` | T |
| ui | destructive / destructiveText | `--destructive` / `--destructive-foreground` | light kind `#dc2626`, dark kind `#f87171` / P |
| ui | input | `--input` | B |
| ui | ring | `--ring` | `color-mix(in oklab, A 60%, P)` |
| ui | sidebarText / sidebarBorder | `--sidebar-foreground` / `--sidebar-border` | T / B |
| ui | commentLine | `--comment-line` | `color-mix(in oklab, <commentMark value> 75%, black)` |
| syntax | comment, keyword, string, title, number, attr | `--hl-<key>` | the kind's set: Light's values for light, Dark's for dark |

Derived values embed the literal colour strings (not `var()` references). `--comment-mark` / `--comment-line` replace the hard-coded `rgb(250 204 21 …)` / `rgb(202 138 4 …)` in the comment-highlight CSS, mixed with transparency at the same alphas as today (built-ins set `commentLine: rgb(202 138 4)` so they look identical). `--tab-strip` replaces the `--strip` computation in `.tab-strip`.

### Task 1: Theme model, built-ins and resolution

**Files:**
- Create: `src/lib/themes/model.ts`, `src/lib/themes/builtin.ts`
- Test: `tests/themes-model.test.ts`

**Interfaces:**
- Produces (in `model.ts`):
  - `type ThemeKind = "light" | "dark"`
  - `MAIN_KEYS`, `EXACT_KEYS`, `UI_KEYS`, `SYNTAX_KEYS`: `readonly` tuples of the key names in the mapping table, in table order.
  - `type MainColors = Record<MainKey, string>`, `ExactColors`, `UiColors`, `SyntaxColors` likewise.
  - `interface Theme { id: string; name: string; kind: ThemeKind; colors: MainColors & Partial<ExactColors>; ui?: Partial<UiColors>; syntax?: Partial<SyntaxColors> }`
  - `type ParseResult = { ok: true; theme: Theme; basedOn?: string; warnings: string[] } | { ok: false; error: string }`
  - `parseTheme(json: string, isColor?: (v: string) => boolean): ParseResult`. A missing `id` gives `id: ""`. The default `isColor` uses `CSS.supports("color", v)` when available, else accepts `#hex` (3/4/6/8 digits) and `rgb/rgba/hsl/hsla/oklch/oklab/lab/lch/color-mix/color(` function syntax.
  - `serializeTheme(t: Theme, extra?: { basedOn?: string }): string` (2-space JSON, `inkyTheme: 1` first, then `id`, `name`, `kind`, `basedOn` if given, `colors`, `ui`, `syntax`; empty groups omitted).
  - `THEME_PROPS: readonly string[]`: every custom property in the "Sets" column, plus `color-scheme` is NOT included (Task 2 sets it from `kind`).
  - `resolveTheme(t: Theme): Record<string, string>`: a value for every entry in `THEME_PROPS`, explicit values first, derived otherwise.
  - `deriveExact(t: Theme): ExactColors`: the exact colours as derived from the main five and kind only (ignores explicit exact values). Task 4 uses it.
- Produces (in `builtin.ts`): `LIGHT`, `DARK`, `BOOK: Theme` and `BUILT_IN: readonly Theme[]` (`[LIGHT, DARK, BOOK]`). Every key of every group is set explicitly, with the values from `src/app.css` at commit `0354808` (`:root` for Light, `.dark` for Dark, `.book` for Book). `tabStrip`: Light and Book `color-mix(in oklab, var(--foreground) 3.5%, var(--background))`, Dark `color-mix(in oklab, black 12%, var(--background))` (as in the current `.tab-strip` rules). `commentMark: rgb(250 204 21)`, `commentLine: rgb(202 138 4)` for all three.
